## 1. Correction to pass 3 §1: the SE/CI/p-value differences were NOT "numerical noise" — they had a precise, demonstrable cause

Pass 3 stated that the small SE/CI/p-value differences between `16_estimate_preliminary.py` (authoritative) and `21_validate_all_primary_cells.py` (independent) were "the expected signature of two different, correct numerical implementations... not a specification disagreement." **This was asserted without actually demonstrating it, and it is corrected here**: the difference has an exact, identified, non-numerical cause.

**The two scripts' declared formulas, read directly from source:**

`16_estimate_preliminary.py` (lines 157–237): weighted within-PSU-cluster demeaning (the cluster is the fixed effect, absorbed by demeaning, not counted in K — the project's own same-group, no-double-penalty convention), CRV1 sandwich `B @ meat @ B`, scalar correction

```
corr = (G / (G - 1)) * ((N - 1) / (N - K))
```

with CIs/p-values from Student's *t* on *G*−1 degrees of freedom.

`21_validate_all_primary_cells.py` (line 124) and `20_validate_pooled_estimate.py` call `PanelOLS.fit(cov_type="clustered", cluster_entity=True, auto_df=True)`. Reading the installed `linearmodels` 7.0 source directly (`.venv/Lib/site-packages/linearmodels/panel/model.py`, `panel/covariance.py`; `shared/covariance.py`):

- `auto_df=True`, with the entity effect nested inside the cluster variable (the same-group case — confirmed via `PanelOLS._determine_df_adjustment` → `_is_effect_nested`), sets `extra_df=0`: this correctly implements the *same* same-group, no-double-penalty degrees-of-freedom convention as the hand-written estimator. This part was already correctly understood in pass 3.
- The covariance's small-sample correction has **two separate pieces**, both read from `ClusteredCovariance`/`HomoskedasticCovariance.__init__` and `cov` (`panel/covariance.py` lines 86–110, 307–339) and `group_debias_coefficient` (`shared/covariance.py` lines 16–42): (i) a `debiased` scale, automatically applied whenever `PanelOLS.fit`'s own default `debiased=True` is in effect: `N / (N - K)` with `extra_df=0`; and (ii) a **separate, opt-in** `group_debias=True` flag applying `(G / (G - 1)) * ((N - 1) / N)`. **`group_debias=True` was never passed** by either `20_validate_pooled_estimate.py` or `21_validate_all_primary_cells.py`.
- Multiplying the two pieces linearmodels *does* apply: `[N/(N-K)] × [(G/(G-1))×(N-1)/N] = (G/(G-1)) × (N-1)/(N-K)` — **algebraically identical** to `16`'s declared `corr` formula. The missing flag, not a different formula and not floating-point/numerical-method noise, is the entire explanation.

**Demonstration, not assertion**: `scripts/historical_wash/24_reconcile_inference_corrections.py` (new, committed) rebuilds all 24 primary cells exactly as `21` does and re-fits each three ways: (a) `21`'s original config (`auto_df=True` only — reproduces the small discrepancy on a fresh run, confirming it is reproducible, not a one-off artefact); (b) the same plus `group_debias=True`; (c) fully uncorrected (`debiased=False, group_debias=False`), to isolate the raw covariance computation from the correction scalars.

**Result, all 24 cells**:

| | Max \|diff\| vs. stored SE | Mean \|diff\| |
|---|---|---|
| (a) `auto_df=True` only (as `21` was run) | 0.0014360 | 0.0002995 |
| (b) `auto_df=True` + `group_debias=True` | **0.0** | **0.0** |

Every one of the 24 cells' SE matches the stored value exactly (to the displayed 8-decimal precision) once `group_debias=True` is added. A direct algebraic check — the uncorrected sandwich SE (config c) multiplied by the manually computed combined scalar `sqrt((G/(G-1))×(N-1)/(N-K))`, compared against linearmodels' own corrected SE (config b) — has a residual of exactly 0.0 for all 24 cells, confirming the derivation above is exact, not approximate. Output: `data/processed/estimation/inference_reconciliation_20261007T184500Z/` (RESTRICTED; `inference_reconciliation_AGGREGATE.csv`, `summary.json`).

**What this does and does not change.** `16_estimate_preliminary.py`'s formula and output were correct throughout — nothing about the authoritative pipeline is revised. What was wrong was the pass-3 explanation of a validation script's own small, previously-unexplained SE gap: it was not "numerical noise" but a single missing keyword argument, now identified, demonstrated, and corrected in a new validation run. `manuscript/v5_2026-10-07/appendices/B_model_specifications_and_independent_verification.md` §B.2 is corrected accordingly (full before/after in that file's own text, not restated here). `21_validate_all_primary_cells.py` and `20_validate_pooled_estimate.py` are left unmodified in their own result-producing logic (preserving the historical record of exactly what was run and what it produced) but each now carries an addendum docstring note pointing to this reconciliation and to script 24, so a future reader does not cite their SE columns as the final word.

## 2. Correction to unsupported "multiplicity" language, Results §5.6 and Discussion §6.1

Both sections previously stated the pooled established-date water–HAZ coefficient "is the one result ... unlikely to be a multiplicity artefact of the [many] cells [estimated]." Independent computational reproduction (confirming a coefficient is correctly computed) does not establish anything about its probability of being one significant draw among many tested cells — that would require an actual multiplicity correction (e.g. Bonferroni, Holm, FDR), which this thesis does not apply anywhere. The claim conflated "computationally verified" with "not a multiplicity artefact" — two unrelated properties.

**Corrected** in `manuscript/v5_2026-10-07/05_results.md` §5.6 and `06_discussion_and_limitations.md` §6.1: both now state plainly that the independent computational check establishes the number is correctly computed, that this is *not* a multiplicity correction, that no such correction has been applied anywhere in this thesis, and that this coefficient's chance of reflecting one significant draw among the cells tested has not been quantified or ruled out. The existing, separately-defensible point already made elsewhere ("chance, given the number of cells estimated" as one of several possible explanations, `06_discussion_and_limitations.md` §6.2) is unaffected and consistent with this correction — the correction only removes the unsupported claim that this specific cell had been shown unlikely to be such a result.

## 3. PDF clipping

See the companion build-fix work in `manuscript/v5_2026-10-07/build/README.md` (rebuilt) for the concrete defects found, the fixes made to `md2tex.py` and the affected `.md` source tables, and the rendered-page verification performed. Summarised here only: the root cause was `md2tex.py`'s table converter using unbounded `l` (left, unwrapped) columns for every table regardless of width, so any table with several columns or a long free-text cell ran off the page — most severely Results §5.6's two historical-coefficient tables (each coefficient cell crammed a CI, *p*-value, and sample size into one unwrapped string) and Appendix A's three-column variable-definition table (long prose/path cells). Fixed by (a) giving every table explicit, content-proportional wrapping column widths, (b) moving sample sizes/cluster counts out of the coefficient cells into a separate table, and (c) allowing inline `\texttt{}` paths to break at `/` and `_`. Confirmed by rendering and visually inspecting the rebuilt PDF, not by text extraction or warning counts alone — the previous build README's claim that the overflow warnings were "cosmetic... no content is clipped" was false and is corrected in the rebuilt README.
